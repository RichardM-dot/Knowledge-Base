# 功率计工程知识点全解（STM32F103C8 + INA226 + CAN + VOFA+）

> 工程源码：`/mnt/data1t/rm/power/power`
> 本文目标：把这个工程涉及的知识点按“从启动到外设、再到协议”的顺序整理成一份可长期查阅的知识库，而不是简单的代码说明。
> 阅读建议：先看第 0 节建立全局图，再按章节顺序看；每个知识点都尽量回答“是什么、为什么、工程里怎么用、容易踩什么坑”。

## 0. 一图看懂整个工程 🧩

```text
                    ┌──────────────────────────────┐
                    │        STM32F103C8T6         │
                    │        72 MHz / 3.3 V        │
                    │                              │
  INA226 ──I2C1────►│ PB6/SCL  PB7/SDA             │
  (电流/电压/功率)   │                              │
                    │ TIM1 500 Hz 更新中断         │
                    │   └─ 每 2 ms 读一次 INA226   │
                    │                              │
                    │ CAN1 PA11/PA12 ──► 1 Mbps    │
                    │   └─ 标准帧 0x605，8 字节    │
                    │                              │
                    │ USART2 PA2/PA3 ──► 115200    │
                    │   └─ DMA1_Channel7           │
                    │   └─ VOFA+ justfloat 20 字节 │
                    └──────────────────────────────┘
```

一次完整的业务周期：

```text
TIM1 每 2 ms 溢出
  → TIM1_UP_IRQHandler()
    → HAL_TIM_IRQHandler()
      → HAL_TIM_PeriodElapsedCallback()      （用户代码，main.c）
        → INA226_Read_ShuntVoltage()         （I2C1 阻塞读）
        → INA226_Read_BusVoltage()
        → INA226_Read_Current()
        → INA226_Read_Power()
        → CAN_send(&hcan, 0x605, ...)        （CAN 发送邮箱）
        → VOFA_justfloat(...)                （USART2 + DMA）
```

**记住一句话：主循环是空的，业务全部在 TIM1 中断回调里完成。**

## 1. 工具链与工程结构 🔧

### 1.1 PlatformIO 工程三要素

`platformio.ini`：

```ini
[env:genericSTM32F103C8]
platform = ststm32
board = genericSTM32F103C8
framework = stm32cube
```

| 配置 | 含义 |
|---|---|
| `platform = ststm32` | 使用 PlatformIO 的 STM32 平台（含编译器、烧录工具、链接脚本） |
| `board = genericSTM32F103C8` | 板卡定义：STM32F103C8T6，64 KB Flash / 20 KB RAM，默认 ST-Link 烧录 |
| `framework = stm32cube` | 使用 STM32Cube HAL 框架，而不是 Arduino 或裸 CMSIS |

板卡定义会自动加入：

```text
-DSTM32F103xB      // 具体型号宏，决定寄存器定义和启动文件
-DSTM32F1          // 系列宏
-DF_CPU=72000000L  // 主频
```

框架还会自动加入：

```text
-DUSE_HAL_DRIVER   // 告诉 stm32f1xx.h 引入 HAL 驱动
```

### 1.2 为什么 `src/` 里没有 `Drivers/`、`system_stm32f1xx.c` 和启动文件？

原 MDK 工程里有：

```text
Drivers/STM32F1xx_HAL_Driver/    // HAL 驱动源码
Drivers/CMSIS/                   // CMSIS 内核与设备头文件
Core/Src/system_stm32f1xx.c      // 系统时钟初始化、SystemCoreClock
MDK-ARM/startup_stm32f103xb.s    // 启动汇编、中断向量表
```

移植到 PlatformIO 后，这些内容由 `framework-stm32cubef1` 提供：

```text
~/.platformio/packages/framework-stm32cubef1/
├── Drivers/STM32F1xx_HAL_Driver/Src/     // 全部 HAL 源文件
├── Drivers/CMSIS/                         // CMSIS 与设备头文件
└── Drivers/CMSIS/Device/ST/STM32F1xx/Source/Templates/
    ├── system_stm32f1xx.c                 // 系统文件
    └── gcc/startup_stm32f103xb.S          // 启动文件
```

**如果再把它们复制进 `src/`：**

- `.c` 文件会参与编译，和框架里的同名函数产生 **multiple definition（重复定义）** 链接错误；
- 启动文件会重复定义中断向量表；
- `system_stm32f1xx.c` 会重复定义 `SystemCoreClock`、`SystemInit()`。

所以本工程 `src/` 只放“应用层 + 外设初始化 + 用户模块”。

### 1.3 MDK 工程与 PlatformIO 工程的对应关系

| 原 MDK 工程 | 移植后位置 | 说明 |
|---|---|---|
| `Core/Src/main.c` | `src/main.c` | 用户主程序 |
| `Core/Src/gpio.c` 等 | `src/gpio.c` 等 | 外设初始化 |
| `Core/Inc/*.h` | `src/*.h` | 头文件 |
| `MDK-ARM/INA226.c/.h` | `src/INA226.c/.h` | 用户模块 |
| `MDK-ARM/CAN_TASK.c/.h` | `src/CAN_TASK.c/.h` | 用户模块 |
| `MDK-ARM/VOFA.c/.h` | `src/VOFA.c/.h` | 用户模块 |
| `Drivers/` | 框架提供 | 不复制 |
| `system_stm32f1xx.c` | 框架提供 | 不复制 |
| `startup_stm32f103xb.s` | 框架提供 | 不复制 |
| `stm32f1xx_hal_conf.h` | 框架生成 | 不复制 |

### 1.4 Linux 大小写与文件编码 ⚠️

**大小写：**

原 MDK 工程在 Windows 下，Windows 文件系统不区分大小写，所以下面这种写法能编译：

```c
#include "CAN_task.h"   // 实际文件是 CAN_TASK.h
#include "ina226.h"     // 实际文件是 INA226.h
```

Linux 文件系统区分大小写，必须写成实际文件名：

```c
#include "CAN_TASK.h"
#include "INA226.h"
```

**编码：**

原工程中文注释是 **GBK/GB18030**，GCC 默认按 **UTF-8** 解析源码。GBK 注释可能导致：

- 编译器报 `stray '\xxx' in program`；
- IDE 显示乱码；
- 某些中文字符的第二个字节恰好是 `\`，把注释提前结束。

移植时已统一转成 **UTF-8**，并在源码里补充了中文注释。

### 1.5 `src/` 为什么是平铺的？

PlatformIO 默认把 `src` 根目录和 `include` 目录加入头文件搜索路径：

```text
CPPPATH = $PROJECT_SRC_DIR + $PROJECT_INCLUDE_DIR
// 只包含这两个目录本身，不递归它们的子目录
```

如果这样放：

```text
src/
├── app/main.c
└── drivers/ina226.c
```

那么 `#include "ina226.h"` 找不到，除非在 `platformio.ini` 里加：

```ini
build_flags = -Isrc/app -Isrc/drivers
```

本工程为了不改 `platformio.ini`，所有 `.c/.h` 都平铺在 `src/` 根目录。

### 1.6 编译、链接与产物

PlatformIO 的 stm32cube 框架大致做这些事：

```text
1. 编译 src/ 下所有 .c
2. 编译 framework 里的 HAL 源文件
3. 编译 framework 里的 system_stm32f1xx.c
4. 汇编 startup_stm32f103xb.S
5. 链接成 .elf
6. 生成 .bin（部分上传方式会再生成 .hex）
```

关键编译/链接参数：

```text
-Os                          // 体积优先优化
-ffunction-sections          // 每个函数单独一个段
-fdata-sections              // 每个变量单独一个段
-Wall                        // 常用警告
-nostdlib                    // 不链接标准启动库
-Wl,--gc-sections            // 链接时删除未使用的段
--specs=nano.specs           // newlib-nano，减小体积
--specs=nosys.specs          // 提供 _write/_sbrk 等系统调用桩
-lc -lgcc -lm -lstdc++ -lnosys
```

`--gc-sections` 的作用：框架里所有 HAL 模块都会编译，但链接时只保留真正被调用的函数，所以不会把没用到的 USB/ADC/SD 驱动塞进固件。

常用命令：

```bash
pio run                 # 编译
pio run -t upload       # 编译并烧录
pio run -t clean        # 清理
pio device monitor -b 115200
```

构建目录：`.pio/build/genericSTM32F103C8/`。

## 2. 启动流程与时钟系统 ⏱️

### 2.1 上电到 `main()` 的完整路径

```text
上电复位
  → 从 0x08000000 取栈顶
  → 从 0x08000004 取 Reset_Handler
  → Reset_Handler（startup_stm32f103xb.S）
      → 初始化 .data / .bss
      → 调用 SystemInit()（system_stm32f1xx.c）
      → 调用 __libc_init_array()（C 库初始化）
      → 调用 main()
```

`SystemInit()` 主要做：

- 设置向量表地址；
- 把 RCC 复位到默认状态（HSI 8 MHz）；
- 设置 Flash 等待周期；
- 更新 `SystemCoreClock`。

真正把主频切到 72 MHz 的，是 `main()` 里的 `SystemClock_Config()`。

### 2.2 HSE、HSI、PLL 是什么？

| 时钟源 | 说明 | 本工程用途 |
|---|---|---|
| HSI | 内部 8 MHz RC 振荡器 | 复位后的默认时钟；HSE 失败时的后备 |
| HSE | 外部 8 MHz 晶振 | 经 PLL ×9 得到 72 MHz |
| PLL | 锁相环倍频器 | HSE × 9 = 72 MHz |

`SystemClock_Config()` 的关键代码：

```c
RCC_OscInitStruct.OscillatorType = RCC_OSCILLATORTYPE_HSE;
RCC_OscInitStruct.HSEState = RCC_HSE_ON;
RCC_OscInitStruct.PLL.PLLState = RCC_PLL_ON;
RCC_OscInitStruct.PLL.PLLSource = RCC_PLLSOURCE_HSE;
RCC_OscInitStruct.PLL.PLLMUL = RCC_PLL_MUL9;     // 8 MHz × 9 = 72 MHz
```

### 2.3 时钟树计算

```text
SYSCLK = HSE × PLLMUL
       = 8 MHz × 9
       = 72 MHz

HCLK   = SYSCLK / AHB_DIV
       = 72 MHz / 1
       = 72 MHz

PCLK1  = HCLK / APB1_DIV
       = 72 MHz / 2
       = 36 MHz

PCLK2  = HCLK / APB2_DIV
       = 72 MHz / 1
       = 72 MHz
```

| 总线 | 频率 | 挂载外设 |
|---|---|---|
| AHB | 72 MHz | DMA、Flash、SRAM |
| APB1 | 36 MHz | CAN1、USART2、I2C1、TIM2~TIM7 |
| APB2 | 72 MHz | GPIO、TIM1、USART1、SPI1 |

**为什么 APB1 要二分频？**

STM32F103 的 APB1 最大频率是 36 MHz，CAN、USART2、I2C1 都挂在 APB1 上。如果 APB1 超过 36 MHz，这些外设可能工作异常。

### 2.4 定时器时钟的“×2”规则

F1 系列有一个容易混淆的规则：

- 如果 APB 预分频系数为 1，定时器时钟 = PCLK；
- 如果 APB 预分频系数不为 1，定时器时钟 = PCLK × 2。

本工程：

```text
APB1 预分频 = 2（不为 1）→ TIM2~TIM7 时钟 = 36 MHz × 2 = 72 MHz
APB2 预分频 = 1（为 1）  → TIM1 时钟    = 72 MHz
```

TIM1 挂在 APB2 上，所以直接是 72 MHz，不涉及 ×2。

### 2.5 Flash 等待周期

```c
HAL_RCC_ClockConfig(&RCC_ClkInitStruct, FLASH_LATENCY_2);
```

72 MHz 属于 48~72 MHz 区间，需要 **2 个 Flash 等待周期**。如果设置太小，CPU 取指会出错；设置太大，性能会下降。

### 2.6 `SystemCoreClock`、SysTick 与 `HAL_Delay()`

`HAL_Init()` 里做了两件与时间有关的事：

```c
HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4);
HAL_InitTick(TICK_INT_PRIORITY);   // TICK_INT_PRIORITY = 15
```

`HAL_InitTick()` 用当前 `SystemCoreClock` 配置 SysTick，使其每 1 ms 中断一次，并把 SysTick 优先级设为 15（最低）。

切换到 72 MHz 后，`HAL_RCC_ClockConfig()` 会：

```c
SystemCoreClock = HAL_RCC_GetSysClockFreq() >> AHBPrescTable[...];
HAL_InitTick(uwTickPrio);   // 用新的主频重新配置 SysTick
```

所以 `HAL_Delay(1)` 仍然是 1 ms，不会因为主频变化而变快或变慢。

**重要结论：**

- `HAL_GetTick()` 的计数依赖 SysTick 中断；
- SysTick 优先级是 15（最低）；
- 如果在一个更高优先级的中断里死等，SysTick 无法抢占，`HAL_GetTick()` 不会增长；
- 任何基于 `HAL_GetTick()` 的超时，在高优先级中断里都可能失效。

这一点和本工程的 I2C 阻塞读有直接关系，见第 7.7 节。

## 3. HAL 库的结构与回调机制 🧱

### 3.1 `HAL_Init()`、`HAL_MspInit()`、`MX_xxx_Init()` 的分工

```text
HAL_Init()
├── 配置 Flash 预取
├── 设置 NVIC 优先级分组
├── 配置 SysTick 1 ms 时基
└── 调用 HAL_MspInit()          // 全局 MSP：AFIO/PWR 时钟、SWD 等

main()
├── SystemClock_Config()        // 时钟树
├── MX_GPIO_Init()              // GPIO 端口时钟
├── MX_DMA_Init()               // DMA1 时钟、NVIC
├── MX_I2C1_Init()              // I2C1 参数 → HAL_I2C_MspInit() 配引脚
├── MX_CAN_Init()               // CAN1 参数 → HAL_CAN_MspInit() 配引脚
├── MX_TIM1_Init()              // TIM1 参数 → HAL_TIM_Base_MspInit() 配时钟/NVIC
└── MX_USART2_UART_Init()       // USART2 参数 → HAL_UART_MspInit() 配引脚/DMA
```

**MSP = MCU Support Package（MCU 支持包）**，可以理解为“HAL 库和具体芯片引脚/时钟之间的胶水层”。

每个外设的 `HAL_xxx_MspInit()` 由对应的 `HAL_xxx_Init()` 自动调用，不需要用户手动调用。

### 3.2 句柄（Handle）是什么？

HAL 用“句柄”管理每个外设实例。句柄是一个结构体，里面包含：

- `Instance`：外设寄存器基地址（如 `CAN1`、`I2C1`、`TIM1`、`USART2`）；
- `Init`：初始化参数；
- `State` / `gState`：当前状态；
- `ErrorCode`：错误码；
- 回调函数指针（如果启用了 register callbacks）；
- 链接的 DMA 句柄等。

本工程的全局句柄：

| 句柄 | 类型 | 定义位置 |
|---|---|---|
| `hcan` | `CAN_HandleTypeDef` | `src/can.c` |
| `hi2c1` | `I2C_HandleTypeDef` | `src/i2c.c` |
| `htim1` | `TIM_HandleTypeDef` | `src/tim.c` |
| `huart2` | `UART_HandleTypeDef` | `src/usart.c` |
| `hdma_usart2_tx` | `DMA_HandleTypeDef` | `src/usart.c` |

`HAL_xxx_Init(&hxxx)` 会把初始化参数写进句柄，并配置寄存器。

### 3.3 弱函数（`__weak`）与回调覆盖 🔑

这是理解 HAL 回调的关键。

HAL 库里定义回调时用了 `__weak`：

```c
__weak void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
  UNUSED(htim);
}
```

`__weak` 的意思是“弱符号”：

- 如果用户没有定义同名函数，链接器使用库里的空实现；
- 如果用户定义了同名函数，链接器使用用户的强符号。

所以你在 `main.c` 里写：

```c
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
  if (htim == &htim1) { ... }
}
```

就能覆盖库里的空函数。

**中断到回调的完整链路：**

```text
TIM1 更新事件
  → NVIC 触发 TIM1_UP_IRQn
    → TIM1_UP_IRQHandler()            // src/stm32f1xx_it.c
      → HAL_TIM_IRQHandler(&htim1)    // HAL 库
        → HAL_TIM_PeriodElapsedCallback(&htim1)  // 你的 main.c
```

### 3.4 `htim == &htim1` 和 `htim->Instance == TIM1` 的区别

两种写法都能判断“是哪个定时器”：

```c
if (htim == &htim1) { ... }              // 比较句柄地址
if (htim->Instance == TIM1) { ... }      // 比较外设实例
```

- `htim == &htim1`：CubeMX 常见写法，直接比较全局句柄地址；
- `htim->Instance == TIM1`：更通用，即使传入的是另一个句柄副本也能判断；
- 如果多个定时器共用回调，建议用 `htim->Instance`，并在 `else if` 中处理其他定时器。

> 相关笔记：同目录下的 `stm32_hal_callback.txt` 用更短的篇幅解释了弱函数与 `htim` 的来源，可以和本节对照阅读。

### 3.5 本工程覆盖了哪些回调？

| 回调 | 位置 | 是否被调用 |
|---|---|---|
| `HAL_TIM_PeriodElapsedCallback()` | `main.c` | ✅ TIM1 更新中断会调用 |
| `HAL_CAN_ErrorCallback()` | `CAN_TASK.c` | ❌ 本工程没有使能错误中断，实际不会调用（见 9.10） |
| `HAL_CAN_RxFifo0MsgPendingCallback()` | 未实现 | ⚠️ RX 中断使能了，但回调为空，见 9.12 |
| `HAL_UART_TxCpltCallback()` | 未实现 | DMA 发送完成会调用，但空实现 |
| `HAL_I2C_ErrorCallback()` | 未实现 | 阻塞式 I2C 不使用回调 |

### 3.6 `USER CODE` 区是什么？

CubeMX 生成的代码用注释标记用户区：

```c
/* USER CODE BEGIN 2 */
/* 用户代码写在这里 */
/* USER CODE END 2 */
```

重新生成代码时，CubeMX 只保留 `USER CODE BEGIN/END` 之间的内容。

本工程的用户代码位置：

- `main.c` 的 `USER CODE BEGIN Includes`：引入 INA226/CAN_TASK/VOFA；
- `main.c` 的 `USER CODE BEGIN PTD`：测量变量；
- `main.c` 的 `USER CODE BEGIN PM`：`HAL_TIM_PeriodElapsedCallback()`；
- `main.c` 的 `USER CODE BEGIN 2`：初始化 INA226、启动 TIM1、配置 CAN 滤波器。

> 习惯上回调函数放在 `USER CODE 4`，本工程放在 `USER CODE PM`，功能上没问题，只要在 USER CODE 区内就能被 CubeMX 保留。

### 3.7 `Error_Handler()` 与断言

```c
void Error_Handler(void)
{
  __disable_irq();
  while (1) { }
}
```

- 所有 `HAL_xxx_Init()` 失败时都会调用它；
- 关闭全局中断并死循环，方便调试器停在这里查看调用栈；
- 产品代码里可以改成“记录错误 → 复位”或“点亮故障灯”。

`assert_failed()` 只有在定义 `USE_FULL_ASSERT` 时才编译。本工程没有定义，所以 `assert_param()` 是空操作。

## 4. GPIO 知识点 🔌

### 4.1 端口时钟必须先使能

STM32 的外设引脚在默认状态下时钟是关闭的。使用任何 GPIO 前必须：

```c
__HAL_RCC_GPIOA_CLK_ENABLE();
__HAL_RCC_GPIOB_CLK_ENABLE();
__HAL_RCC_GPIOD_CLK_ENABLE();
```

本工程在 `MX_GPIO_Init()` 中使能 GPIOD/GPIOA/GPIOB。

> GPIOD 时钟是因为 CubeMX 把 PD0/PD1（HSE 晶振引脚）也算在 GPIO 配置里；实际上它们是 OSC_IN/OSC_OUT，使能 GPIOD 时钟无害。

### 4.2 本工程用到的 GPIO 模式

| 引脚 | 功能 | 模式 | 说明 |
|---|---|---|---|
| PA11 | CAN_RX | 输入浮空 | 由 CAN 收发器驱动 |
| PA12 | CAN_TX | 复用推挽输出 | 输出到 CAN 收发器 |
| PB6 | I2C1_SCL | 复用开漏 | 需要外部上拉 |
| PB7 | I2C1_SDA | 复用开漏 | 需要外部上拉 |
| PA2 | USART2_TX | 复用推挽输出 | 输出到上位机/模块 |
| PA3 | USART2_RX | 输入浮空 | 接收上位机数据 |
| PA13 | SWDIO | 调试口 | SWD 数据 |
| PA14 | SWCLK | 调试口 | SWD 时钟 |

对应的 HAL 配置：

```c
/* 复用推挽输出 */
GPIO_InitStruct.Mode = GPIO_MODE_AF_PP;
GPIO_InitStruct.Speed = GPIO_SPEED_FREQ_HIGH;

/* 复用开漏输出 */
GPIO_InitStruct.Mode = GPIO_MODE_AF_OD;

/* 输入浮空 */
GPIO_InitStruct.Mode = GPIO_MODE_INPUT;
GPIO_InitStruct.Pull = GPIO_NOPULL;
```

### 4.3 为什么 I2C 要“开漏”？

I2C 总线是多主多从结构，SCL/SDA 都是**线与**：

- 任何一个设备拉低，总线就是低；
- 所有设备都释放，总线由上拉电阻拉高。

因此 SCL/SDA 必须配置为**开漏输出（Open-Drain）**，不能推挽。推挽输出高电平时会主动驱动高电平，和另一个拉低的设备“打架”，可能损坏引脚。

### 4.4 为什么 CAN_RX 是输入、CAN_TX 是复用推挽？

- CAN 控制器需要从收发器接收差分信号转换后的逻辑电平 → PA11 作为输入；
- CAN 控制器输出的 TX 信号需要送到收发器 → PA12 作为复用推挽输出。

STM32 的 CAN 引脚本身不是差分信号，必须外接 CAN 收发器（如 TJA1050、SN65HVD230、MCP2551）。

### 4.5 `__HAL_AFIO_REMAP_SWJ_NOJTAG()`

```c
__HAL_AFIO_REMAP_SWJ_NOJTAG();
```

作用：

- 关闭 JTAG-DP；
- 保留 SW-DP（SWDIO/SWCLK）；
- 释放 PA15、PB3、PB4 作为普通 GPIO（如果以后需要）。

本工程用 SWD 调试，所以保留 SWD 是正确的。

## 5. NVIC 与中断系统 ⚡

### 5.1 中断向量表与 `IRQHandler`

启动文件里有一张中断向量表，把每个中断号映射到一个函数名。例如：

```text
TIM1_UP_IRQHandler
USB_LP_CAN1_RX0_IRQHandler
DMA1_Channel7_IRQHandler
USART2_IRQHandler
```

这些函数在启动文件里是**弱定义**（指向默认死循环）。用户在 `stm32f1xx_it.c` 里写同名函数，就会覆盖弱定义。

### 5.2 NVIC 优先级分组

`HAL_Init()` 设置：

```c
HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4);
```

含义：

- 4 位全部用于**抢占优先级**（preemption priority）；
- 0 位用于子优先级（subpriority）；
- 抢占优先级数值越小，优先级越高；
- 高抢占优先级可以打断低抢占优先级的中断；
- 相同抢占优先级的中断不能互相打断。

STM32F1 的 `__NVIC_PRIO_BITS = 4`，所以优先级范围是 0~15。

### 5.3 本工程的中断优先级

| 中断 | 优先级 | 说明 |
|---|---|---|
| `TIM1_UP_IRQn` | 0（最高） | 2 ms 采样节拍 |
| `DMA1_Channel7_IRQn` | 0 | USART2_TX DMA |
| `USART2_IRQn` | 1 | 串口中断 |
| `USB_LP_CAN1_RX0_IRQn` | 2 | CAN RX0 |
| `SysTick_IRQn` | 15（最低） | HAL 1 ms 时基 |

**注意：**

- TIM1 和 DMA1_CH7 都是 0，不能互相抢占；
- TIM1 中断里阻塞太久，会推迟 DMA/USART/CAN/SysTick 的响应；
- SysTick 优先级最低，所以在高优先级中断里 `HAL_GetTick()` 不增长。

### 5.4 中断服务函数（ISR）的编写原则

1. **短**：只做必要的事，复杂逻辑放到主循环或任务里；
2. **不阻塞**：不要 `HAL_Delay()`、不要死等标志位；
3. **不调用不可重入函数**：如 `printf()`、动态内存分配；
4. **共享变量加 `volatile`**：如果主循环和 ISR 都会访问；
5. **清除中断标志**：HAL 通常会帮你清，但要知道哪些标志需要手动清；
6. **注意优先级**：高优先级 ISR 会阻塞低优先级 ISR 和 SysTick。

### 5.5 中断风暴是什么？

如果 ISR 没有清除中断源，CPU 退出中断后会立刻再次进入，形成“中断风暴”，主循环永远得不到执行。

本工程有一个潜在风险：CAN RX 中断使能了，但没有实现读取报文的回调，见 9.12。

## 6. 定时器 TIM1 与 500 Hz 采样节拍 ⏲️

### 6.1 定时器基本公式

```text
更新频率 = 定时器时钟 / (Prescaler + 1) / (Period + 1)
更新周期 = 1 / 更新频率
```

本工程：

```text
定时器时钟 = 72 MHz
Prescaler = 71
Period = 1999

更新频率 = 72 MHz / 72 / 2000
         = 1 MHz / 2000
         = 500 Hz
更新周期 = 2 ms
```

### 6.2 关键初始化字段

```c
htim1.Instance = TIM1;
htim1.Init.Prescaler = 71;                    // 72 MHz / 72 = 1 MHz
htim1.Init.CounterMode = TIM_COUNTERMODE_UP;  // 向上计数
htim1.Init.Period = 1999;                     // 2000 个计数
htim1.Init.ClockDivision = TIM_CLOCKDIVISION_DIV1;
htim1.Init.RepetitionCounter = 0;
htim1.Init.AutoReloadPreload = TIM_AUTORELOAD_PRELOAD_DISABLE;
```

| 字段 | 含义 |
|---|---|
| `Prescaler` | 预分频，实际分频系数 = 值 + 1 |
| `Period` | 自动重装值，实际计数周期 = 值 + 1 |
| `CounterMode` | 向上/向下/中央对齐 |
| `ClockDivision` | 死区/滤波时钟分频，不影响计数器时钟 |
| `RepetitionCounter` | 高级定时器重复计数，0 表示每次溢出都产生更新事件 |
| `AutoReloadPreload` | ARR 预装载，DISABLE 表示写入立即生效 |

### 6.3 启动定时器

```c
HAL_TIM_Base_Start_IT(&htim1);
```

- `HAL_TIM_Base_Start()`：只启动计数，不使能更新中断；
- `HAL_TIM_Base_Start_IT()`：启动计数并使能更新中断（UIE）；
- 本工程需要 2 ms 回调，所以用 `_IT` 版本。

### 6.4 更新中断到回调

```text
TIM1 计数器溢出
  → 置位 UIF（更新中断标志）
    → NVIC 触发 TIM1_UP_IRQn
      → TIM1_UP_IRQHandler()
        → HAL_TIM_IRQHandler(&htim1)
          → 清除 UIF
          → HAL_TIM_PeriodElapsedCallback(&htim1)
```

### 6.5 为什么选 500 Hz？

- INA226 在 `0x0417` 配置下，一次“总线 + 分流”转换约 1.24 ms；
- 2 ms 采样周期比转换时间略长，能拿到较新的数据；
- 对电源参数监测来说，500 Hz 已经足够；
- CAN 1 Mbps、UART 115200 都能承受 500 Hz 的发送速率。

### 6.6 多个定时器共用一个回调

如果以后增加 TIM2，可以这样写：

```c
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
  if (htim->Instance == TIM1) {
    /* TIM1 的 2 ms 任务 */
  } else if (htim->Instance == TIM2) {
    /* TIM2 的任务 */
  }
}
```

不要用 `htim == &htim1` 和 `htim == &htim2` 之外的方式遗漏判断，否则每个定时器中断都会执行同一段代码。

## 7. I2C 总线与 INA226 通信 📡

### 7.1 I2C 物理层

- 两根线：SCL（时钟）、SDA（数据）；
- 开漏输出 + 上拉电阻；
- 支持多主多从；
- 标准模式 100 kHz，快速模式 400 kHz；
- 本工程使用 400 kHz。

**上拉电阻：**

- INA226 模块通常自带 4.7 kΩ 或 10 kΩ 上拉；
- 如果自己画板，PB6/PB7 需要上拉到 3.3 V；
- 上拉太小会增加功耗，太大上升沿变慢，400 kHz 下一般 2.2~4.7 kΩ。

### 7.2 7 位地址与 8 位地址

INA226 的 7 位地址由 A0/A1 决定：

| A1 | A0 | 7 位地址 |
|---|---|---|
| GND | GND | 0x40 |
| GND | VCC | 0x41 |
| VCC | GND | 0x42 |
| VCC | VCC | 0x43 |

HAL 的 I2C API 使用 **8 位地址**（7 位地址左移一位）：

```text
0x40 << 1 = 0x80
```

所以代码里写：

```c
#define INA226_I2C_ADDR 0x80
```

如果你写 `0x40`，HAL 会把它当成 8 位地址，实际访问的是 7 位地址 `0x20`，INA226 不会应答。

### 7.3 I2C1 初始化要点

```c
hi2c1.Instance = I2C1;
hi2c1.Init.ClockSpeed = 400000;                 // 400 kHz
hi2c1.Init.DutyCycle = I2C_DUTYCYCLE_2;         // 快速模式 2:1
hi2c1.Init.OwnAddress1 = 0;                     // 主机模式不用
hi2c1.Init.AddressingMode = I2C_ADDRESSINGMODE_7BIT;
hi2c1.Init.DualAddressMode = I2C_DUALADDRESS_DISABLE;
hi2c1.Init.GeneralCallMode = I2C_GENERALCALL_DISABLE;
hi2c1.Init.NoStretchMode = I2C_NOSTRETCH_DISABLE;
```

- `ClockSpeed = 400000`：HAL 会根据 APB1 时钟计算 CCR/TRISE；
- `DutyCycle = 2`：快速模式低电平/高电平比例为 2:1；
- `NoStretchMode = DISABLE`：允许从机拉低 SCL 做时钟延展，兼容性更好；
- 主机模式不需要自己的地址。

### 7.4 `HAL_I2C_Mem_Read()` / `HAL_I2C_Mem_Write()`

这两个函数用于“带寄存器地址”的 I2C 设备，例如 INA226、EEPROM、传感器：

```c
HAL_I2C_Mem_Read(hi2c, DevAddress, MemAddress, MemAddressSize,
                 pData, Size, Timeout);
```

参数含义：

| 参数 | 本工程取值 | 说明 |
|---|---|---|
| `hi2c` | `&hi2c1` | I2C 句柄 |
| `DevAddress` | `0x80` | 8 位从机地址 |
| `MemAddress` | `INA226_REG_xxx` | 寄存器地址（0x00~0x05） |
| `MemAddressSize` | `1` | 寄存器地址 1 字节 |
| `pData` | 接收缓冲区 | 2 字节 |
| `Size` | `2` | 读/写 2 字节 |
| `Timeout` | `100` | 超时 100 ms |

写寄存器的时序：

```text
START → 设备地址+W → ACK → 寄存器地址 → ACK → 数据高字节 → ACK → 数据低字节 → ACK → STOP
```

读寄存器的时序：

```text
START → 设备地址+W → ACK → 寄存器地址 → ACK
      → 重复 START → 设备地址+R → ACK → 数据高字节 → ACK → 数据低字节 → NACK → STOP
```

### 7.5 I2C 常见故障排查

| 现象 | 可能原因 | 排查方法 |
|---|---|---|
| `HAL_I2C_Mem_Read` 返回 `HAL_ERROR` | 设备没应答 | 检查供电、地址、A0/A1、接线 |
| 一直忙/超时 | SDA/SCL 被拉低 | 示波器/逻辑分析仪看波形，检查上拉 |
| 读到的数据全 0 | 地址错、寄存器错、设备没初始化 | 用 I2C 扫描程序确认地址 |
| 偶尔出错 | 上拉太弱、线太长、干扰 | 减小上拉、缩短线、加屏蔽 |
| 多设备冲突 | 地址重复 | 改 A0/A1 或改用 I2C 多路复用器 |

**I2C 扫描思路：**

```c
for (uint8_t addr = 1; addr < 128; addr++) {
    if (HAL_I2C_IsDeviceReady(&hi2c1, addr << 1, 3, 10) == HAL_OK) {
        // 找到设备
    }
}
```

### 7.6 阻塞、中断、DMA 三种 I2C 方式

| 方式 | API | 特点 |
|---|---|---|
| 阻塞（轮询） | `HAL_I2C_Mem_Read()` | 简单，CPU 原地等待 |
| 中断 | `HAL_I2C_Mem_Read_IT()` | 非阻塞，需要回调 |
| DMA | `HAL_I2C_Mem_Read_DMA()` | 非阻塞，适合大量数据 |

本工程使用阻塞方式，因为每次只读 2 字节，代码简单。

### 7.7 ⚠️ 本工程的隐患：在 TIM1 中断里阻塞读 I2C

`HAL_TIM_PeriodElapsedCallback()` 在 TIM1 中断（优先级 0）里调用 4 次 `HAL_I2C_Mem_Read()`。

**时间估算（400 kHz）：**

- 1 字节 = 8 数据位 + 1 ACK = 9 个时钟 = 22.5 µs；
- 一次读 = 设备地址 + 寄存器地址 + 2 数据字节 ≈ 4 字节 ≈ 90 µs；
- 4 次读 ≈ 360 µs，加上 HAL 开销约 0.4~0.5 ms；
- 占 2 ms 周期的 20%~25%。

**风险：**

- `HAL_I2C_Mem_Read()` 的超时基于 `HAL_GetTick()`；
- SysTick 优先级 15，无法抢占 TIM1（优先级 0）；
- 如果 I2C 总线被拉死，`HAL_GetTick()` 不增长，超时永远不到，ISR 可能卡死；
- 即使正常，0.4 ms 的阻塞也会推迟 USART/CAN/SysTick 响应。

**改进方向：**

- 把 I2C 读取移到主循环，用标志位触发；
- 使用 I2C DMA + 状态机；
- 降低 TIM1 中断优先级，或把采样放到较低优先级任务；
- 给 I2C 增加总线恢复逻辑（发送 9 个时钟脉冲）。

## 8. INA226 电流/电压/功率监测芯片 🔋

### 8.1 INA226 是什么？

INA226 是 TI 的高侧/低侧电流与总线电压监测芯片，内部包含：

- 分流电压 ADC（测量采样电阻两端压降）；
- 总线电压 ADC（测量负载端电压）；
- 功率计算单元；
- 校准寄存器；
- I2C 接口；
- 报警/转换就绪引脚（本工程未用）。

它适合：

- 电源输入/输出监测；
- 电池充放电监测；
- 电机/负载功率监测；
- 太阳能/DC-DC 效率测量。

### 8.2 采样电阻与测量原理

```text
Vbus ──┬──── R_shunt ────┬── Vload
       │                 │
      IN+               IN-
       │                 │
      INA226 测量 (IN+ - IN-) = Vshunt
       │
      GND
```

- 电流流过采样电阻产生压降：`Vshunt = I × Rshunt`；
- INA226 测量 `Vshunt` 和 `Vbus`；
- 内部根据校准值计算电流：`I = Vshunt / Rshunt`（通过 CAL 寄存器换算）；
- 功率：`P = Vbus × I`（内部计算）。

采样电阻的选择：

- 阻值越大，电流分辨率越高，但压降和功耗越大；
- 阻值越小，压降越小，但分辨率越低；
- 本工程默认 1 mΩ，板级表中有 0.9897 mΩ 等值。

### 8.3 寄存器地图

| 地址 | 名称 | 读写 | 说明 |
|---|---|---|---|
| 0x00 | Configuration | R/W | 配置：平均次数、转换时间、模式 |
| 0x01 | Shunt Voltage | R | 分流电压，有符号，LSB = 2.5 µV |
| 0x02 | Bus Voltage | R | 总线电压，无符号，LSB = 1.25 mV |
| 0x03 | Power | R | 功率，无符号，LSB = 25 × Current_LSB |
| 0x04 | Current | R | 电流，有符号，LSB = Current_LSB |
| 0x05 | Calibration | R/W | 校准值 |
| 0x06 | Mask/Enable | R/W | 报警屏蔽/使能（本工程未用） |
| 0x07 | Alert Limit | R/W | 报警阈值（本工程未用） |
| 0xFE | Manufacturer ID | R | 厂商 ID（0x5449，本工程未读） |
| 0xFF | Die ID | R | 芯片 ID（0x2260，本工程未读） |

### 8.4 配置寄存器 `0x0417` 的字段解码

```text
0x0417 = 0000 0100 0001 0111
```

| 位 | 字段 | 值 | 含义 |
|---|---|---|---|
| 15 | RST | 0 | 不复位 |
| 14 | 保留 | 0 | — |
| 13:11 | AVG | 000 | 平均 1 次 |
| 10:8 | VBUSCT | 100 | 总线电压转换时间 1.1 ms |
| 7:5 | VSHCT | 000 | 分流电压转换时间 140 µs |
| 4:3 | 保留 | 10 | 原工程写入值，保留位 |
| 2:0 | MODE | 111 | 分流 + 总线，连续转换 |

**转换时间与更新率：**

```text
一次“总线 + 分流”转换 ≈ 1.1 ms + 0.14 ms = 1.24 ms
更新率 ≈ 1 / 1.24 ms ≈ 806 Hz
```

本工程 500 Hz 读取，数据是够新的。

> 注意：`0x0417` 的 bit4 是保留位，原工程写了 1。多数情况下芯片会忽略保留位，但更规范的做法是写 0（例如 `0x0407` 仍保持相同字段）。

### 8.5 校准公式：Current_LSB 与 CAL

INA226 不会直接知道采样电阻多大，需要你告诉它一个校准值。

**第一步：选择 Current_LSB**

```text
Current_LSB = 最大测量电流 / 32767
```

本工程：

```text
Current_LSB = 32.7 A / 32767 ≈ 0.000998 A ≈ 0.998 mA
```

> 数据手册写的是除以 2^15 = 32768；工程用 32767，差异约 0.003%，可以忽略。

**第二步：计算 CAL**

```text
CAL = 0.00512 / (Current_LSB × R_SHUNT)
```

其中 `0.00512 = 2.5 µV × 2048` 是芯片内部常数。

本工程默认 `R_SHUNT = 1 mΩ`：

```text
CAL ≈ 0.00512 / (0.000998 × 0.001)
    ≈ 5131
```

板级表 `0.0009897 Ω`：

```text
CAL ≈ 0.00512 / (0.000998 × 0.0009897)
    ≈ 5184
```

CAL 是 16 位寄存器，范围 0~65535。如果采样电阻太小，CAL 可能溢出，需要重新选择 `Current_LSB` 或增大采样电阻。

### 8.6 各寄存器的 LSB 与量程

| 测量项 | LSB | 原始值类型 | 满量程 |
|---|---|---|---|
| 分流电压 | 2.5 µV | 有符号 16 位 | ±81.92 mV |
| 总线电压 | 1.25 mV | 无符号 16 位 | 40.96 V |
| 电流 | Current_LSB ≈ 0.998 mA | 有符号 16 位 | ±32.7 A（设计值） |
| 功率 | 25 × Current_LSB ≈ 24.95 mW | 无符号 16 位 | ≈ 1635 W（寄存器满量程） |

**换算代码：**

```c
分流电压 = raw_shunt * 2.5e-6f;        // V
总线电压 = raw_bus   * 1.25e-3f;       // V
电流     = raw_current * Current_LSB;  // A
功率     = raw_power * 25.0f * Current_LSB; // W
```

### 8.7 板级 UID 映射：一份固件适配多块板

`INA226.c` 里有一张表：

```c
static const BoardConfig_t board_conf[] = {
    {0x0664FF54, 0.0009897f},
    {0x87654321, 0.005f},
    {0x11223344, 0.010f},
};
```

初始化时：

```c
mcu_id = HAL_GetUIDw0();   // 读取 96 位唯一 ID 的低 32 位

for (i = 0; i < BOARD_CONF_COUNT; i++) {
    if (board_conf[i].uid == mcu_id) {
        current_r_shunt = board_conf[i].r_shunt;
        break;
    }
}
```

**为什么这样做？**

- 不同功率板可能使用不同阻值的采样电阻；
- 同一份固件烧到不同板子上，根据 MCU 唯一 ID 自动选择正确的电阻；
- 如果 UID 不在表中，使用默认 `INA226_R_SHUNT`（1 mΩ）。

**注意：**

- 表中的 UID 是示例值，实际使用时要替换成自己板子的 UID；
- `HAL_GetUIDw0()` 返回低 32 位，`HAL_GetUIDw1()`/`HAL_GetUIDw2()` 返回更高位；
- 唯一 ID 在芯片出厂时固化，不会改变。

### 8.8 初始化流程

```text
INA226_Init()
├── 读取 MCU UID
├── 查表得到 R_SHUNT
├── 计算 Current_LSB
├── 计算 CAL
├── 写配置寄存器 0x0417
└── 写校准寄存器 CAL
```

**注意：**

- 先写配置，再写校准；
- 两次写操作都是 2 字节、高字节在前；
- 如果配置写失败，直接返回，不写校准；
- `main()` 里没有检查返回值，这是原工程的简化处理。

### 8.9 数据读取流程

```c
shunt_volt = INA226_Read_ShuntVoltage(&hi2c1);
bus_volt   = INA226_Read_BusVoltage(&hi2c1);
current    = INA226_Read_Current(&hi2c1);
power      = INA226_Read_Power(&hi2c1);
```

每个函数：

1. 用 `HAL_I2C_Mem_Read()` 读 2 字节；
2. 组合成 16 位原始值（高字节在前）；
3. 乘以对应 LSB；
4. 读失败返回 `0.0f`。

**读失败的隐患：**

- 返回 `0.0f` 和“真实测量值为 0”无法区分；
- 如果传感器掉线，上位机会看到 0 V / 0 A，可能误判；
- 改进：返回 `HAL_StatusTypeDef` + 输出参数，或用 NaN 表示无效。

### 8.10 INA226 相关注意事项

1. **总线电压寄存器是无符号的**，但代码用 `int16_t raw_v` 存储；0~36 V 时 raw 最大 28800，仍是正数，没问题；超过 40.96 V 会回绕。
2. **功率寄存器是无符号的**，但代码用 `int16_t raw_p` 存储；功率超过约 817 W 时 raw 超过 32767，会变成负数。
3. **电流寄存器是有符号的**，`int16_t` 正确。
4. **分流电压寄存器是有符号的**，`int16_t` 正确。
5. **没有读取 Manufacturer ID / Die ID**：无法确认芯片是否真的存在、型号是否匹配。
6. **没有等待转换就绪**：连续模式下一般没问题，但上电第一次读取可能拿到旧数据。
7. **没有软件复位**：如果芯片状态异常，可以写配置寄存器的 RST 位复位。

## 9. CAN 总线通信 🚌

### 9.1 CAN 物理层

CAN 使用两根差分线：

- CAN_H；
- CAN_L；
- 差分电压表示显性（0）和隐性（1）；
- 抗干扰能力强，适合汽车/工业环境；
- 总线两端各需要 **120 Ω 终端电阻**；
- STM32 的 CAN_TX/CAN_RX 是逻辑电平，必须外接收发器（TJA1050、SN65HVD230、MCP2551 等）。

**接线示意：**

```text
STM32 PA12 (TX) ──► 收发器 TXD
STM32 PA11 (RX) ◄── 收发器 RXD
收发器 CANH ────── 双绞线 ────── CANH
收发器 CANL ────── 双绞线 ────── CANL
两端各 120 Ω
```

### 9.2 CAN 位定时公式

```text
位时间 = 1 / 波特率
       = (1 + BS1 + BS2) × tq
tq     = Prescaler / CAN输入时钟
```

其中：

- `1` 是同步段（Sync Seg）；
- `BS1` 是时间段 1；
- `BS2` 是时间段 2；
- `SJW` 是重同步跳转宽度。

本工程：

```text
CAN 输入时钟 = APB1 = 36 MHz
Prescaler = 2
tq = 2 / 36 MHz = 55.56 ns

总 TQ 数 = 1 + 16 + 1 = 18
位时间 = 18 × 55.56 ns = 1 µs
波特率 = 1 / 1 µs = 1 Mbps
```

采样点：

```text
采样点 = (1 + BS1) / 总 TQ
       = (1 + 16) / 18
       = 94.4%
```

> 94.4% 偏高。CAN 常用采样点是 87.5%（CiA 推荐）。如果 1 Mbps 通信不稳定，可以调整 BS1/BS2，例如 BS1=13、BS2=4、总 TQ=18，采样点 = 14/18 = 77.8%；或 BS1=14、BS2=3，采样点 = 83.3%。原工程使用 16/1，先按原样理解，实际调试时再优化。

### 9.3 CAN 帧格式

标准数据帧：

```text
SOF | 标识符(11位) | RTR | IDE | 保留 | DLC | 数据(0~8字节) | CRC | ACK | EOF
```

| 字段 | 含义 |
|---|---|
| SOF | 帧起始，1 位显性 |
| 标识符 | 11 位标准 ID 或 29 位扩展 ID |
| RTR | 0 = 数据帧，1 = 远程帧 |
| IDE | 0 = 标准帧，1 = 扩展帧 |
| DLC | 数据长度，0~8 |
| 数据 | 最多 8 字节 |
| CRC | 15 位校验 |
| ACK | 接收方应答 |
| EOF | 帧结束，7 位隐性 |

本工程：

```c
tx.DLC = 0x08;          // 8 字节
tx.IDE = CAN_ID_STD;    // 标准帧
tx.RTR = CAN_RTR_DATA;  // 数据帧
tx.StdId = stdid;       // 11 位 ID
tx.ExtId = 0x000;       // 标准帧下忽略
```

### 9.4 标准帧与扩展帧

| 类型 | ID 位数 | IDE | 本工程 |
|---|---|---|---|
| 标准帧 | 11 位（0~0x7FF） | 0 | ✅ 使用 |
| 扩展帧 | 29 位 | 1 | ❌ 未使用 |

本工程 ID 为 `0x605`，在 11 位范围内（0x7FF = 2047）。

### 9.5 发送邮箱与 `HAL_CAN_AddTxMessage()`

STM32F1 的 CAN 有 **3 个发送邮箱**。调用：

```c
uint32_t mailbox = 0;
HAL_CAN_AddTxMessage(&hcan, &tx, Data, &mailbox);
```

HAL 会：

1. 检查是否有空邮箱；
2. 选择一个空邮箱；
3. 写入 ID、DLC、数据；
4. 置位发送请求；
5. 返回邮箱掩码（`1 << 邮箱号`）。

如果 3 个邮箱都满，返回 `HAL_BUSY`，本次数据不会发送。

**发送优先级：**

```c
hcan.Init.TransmitFifoPriority = DISABLE;   // TXFP = 0
```

- `DISABLE`（TXFP=0）：按**报文 ID 优先级**发送，ID 越小越优先；
- `ENABLE`（TXFP=1）：按**请求顺序**发送（FIFO）。

本工程是 DISABLE，所以如果同时有多个邮箱待发，ID 小的先发。

### 9.6 验收滤波器

CAN 控制器会把总线上所有帧先收下来，再根据滤波器决定是否放进 FIFO。

本工程：

```c
sFilterConfig.FilterBank = 0;
sFilterConfig.FilterMode = CAN_FILTERMODE_IDMASK;   // 掩码模式
sFilterConfig.FilterScale = CAN_FILTERSCALE_32BIT;  // 32 位
sFilterConfig.FilterIdHigh = 0x0000;
sFilterConfig.FilterIdLow = 0x0000;
sFilterConfig.FilterMaskIdHigh = 0x0000;
sFilterConfig.FilterMaskIdLow = 0x0000;
sFilterConfig.FilterFIFOAssignment = CAN_RX_FIFO0;
sFilterConfig.FilterActivation = ENABLE;
sFilterConfig.SlaveStartFilterBank = 14;
```

**掩码模式规则：**

```text
mask 位 = 1：该位必须与 ID 匹配
mask 位 = 0：该位不关心
```

掩码全 0 → 所有位都不关心 → **接收所有帧**。

**FilterBank = 0：** 使用第 0 组滤波器。

**FilterScale = 32BIT：** 一个滤波器组使用 32 位。

**FIFO0：** 匹配的帧放入接收 FIFO0。

**SlaveStartFilterBank = 14：** 这是给双 CAN（F105/107）用的，F103 单 CAN 会忽略。

### 9.7 本工程的 CAN 数据协议

```text
标准帧 ID = 0x605
DLC = 8

Byte 0..1：分流电压，int16，大端，单位 mV
Byte 2..3：总线电压，int16，大端，单位 mV
Byte 4..5：电流，int16，大端，单位 mA
Byte 6..7：功率，int16，大端，单位 0.01 W
```

打包代码：

```c
Data[0] = ((num1) >> 8);
Data[1] = (num1);
Data[2] = ((num2) >> 8);
Data[3] = (num2);
Data[4] = ((num3) >> 8);
Data[5] = (num3);
Data[6] = ((num4) >> 8);
Data[7] = (num4);
```

### 9.8 为什么 CAN 数据用“大端”？

CAN 协议本身没有规定数据字节的端序，端序由应用层约定。本工程选择：

```text
高字节在前（大端）
```

接收方需要：

```c
int16_t value = (int16_t)((Data[0] << 8) | Data[1]);
```

**注意：**

- STM32 是小端 CPU，但 CAN 数据区是字节数组，代码手动拆分，所以不受 CPU 端序影响；
- 如果直接把 `int16_t*` 强转成 `uint8_t*` 发送，得到的是小端序，和本工程协议不一致；
- 跨平台通信时，端序一定要写清楚。

### 9.9 CAN 错误状态与 Bus-Off

CAN 有两种错误计数：

- TEC（发送错误计数器）；
- REC（接收错误计数器）。

状态迁移：

```text
Error Active（正常）
  → TEC 或 REC > 95：Error Warning
  → TEC 或 REC > 127：Error Passive
  → TEC > 255：Bus-Off（总线关闭）
```

Bus-Off 后，节点不再发送/接收。恢复条件：

- 硬件自动恢复（`AutoBusOff = ENABLE`）：检测到 128 次连续 11 位隐性位后自动恢复；
- 软件恢复：停止 CAN，再启动 CAN。

本工程：

```c
hcan.Init.AutoBusOff = ENABLE;
```

同时写了：

```c
void HAL_CAN_ErrorCallback(CAN_HandleTypeDef *hcan)
{
    if (hcan->Instance->ESR & CAN_ESR_BOFF)
    {
        HAL_CAN_Stop(hcan);
        HAL_CAN_Start(hcan);
    }
}
```

### 9.10 ⚠️ 为什么 `HAL_CAN_ErrorCallback()` 实际不会执行？

`HAL_CAN_ErrorCallback()` 由 `HAL_CAN_IRQHandler()` 在“错误中断”分支里调用。要让它执行，需要同时满足：

1. CAN 外设的 `ERRIE`（错误中断使能）被置位；
2. NVIC 的 `CAN1_SCE_IRQn`（状态变化/错误中断）被使能；
3. 中断服务函数 `CAN1_SCE_IRQHandler()` 调用 `HAL_CAN_IRQHandler()`。

本工程：

- `CAN_Filter_Init()` 只使能了：
  - `CAN_IT_RX_FIFO0_MSG_PENDING`
  - `CAN_IT_TX_MAILBOX_EMPTY`
  - **没有** `CAN_IT_ERROR` / `CAN_IT_BUSOFF`；
- NVIC 只使能了 `USB_LP_CAN1_RX0_IRQn`（CAN1 RX0）；
- 错误中断在 `CAN1_SCE_IRQn`（中断号 22），没有使能，也没有实现 `CAN1_SCE_IRQHandler()`。

结论：

```text
HAL_CAN_ErrorCallback() 是“死代码”，不会被调用。
```

但 `AutoBusOff = ENABLE` 仍然有效，硬件会自动从 Bus-Off 恢复。所以原工程即使回调不执行，CAN 也能恢复。

**如果要让错误回调生效：**

```c
HAL_CAN_ActivateNotification(&hcan,
    CAN_IT_ERROR | CAN_IT_BUSOFF | CAN_IT_LAST_ERROR_CODE);

HAL_NVIC_SetPriority(CAN1_SCE_IRQn, 2, 0);
HAL_NVIC_EnableIRQ(CAN1_SCE_IRQn);
```

并实现：

```c
void CAN1_SCE_IRQHandler(void)
{
    HAL_CAN_IRQHandler(&hcan);
}
```

### 9.11 CAN 中断向量映射（F103）

| 功能 | 中断号 | 向量名 | 本工程 |
|---|---|---|---|
| CAN1 TX | 19 | `USB_HP_CAN1_TX_IRQn` | ❌ 未使能 |
| CAN1 RX0 | 20 | `USB_LP_CAN1_RX0_IRQn` | ✅ 使能 |
| CAN1 RX1 | 21 | `CAN1_RX1_IRQn` | ❌ 未使能 |
| CAN1 SCE（错误） | 22 | `CAN1_SCE_IRQn` | ❌ 未使能 |

**注意：**

- `USB_HP_CAN1_TX` 和 `USB_LP_CAN1_RX0` 是 USB 与 CAN 共用的向量；
- 如果同时使用 USB 和 CAN，中断服务函数里要判断中断源；
- 本工程只使能 RX0，所以只处理接收 FIFO0。

### 9.12 ⚠️ CAN RX 中断风暴风险

本工程：

- 滤波器全通过；
- 使能了 `CAN_IT_RX_FIFO0_MSG_PENDING`；
- 使能了 `USB_LP_CAN1_RX0_IRQn`；
- **没有实现 `HAL_CAN_RxFifo0MsgPendingCallback()`**。

`HAL_CAN_IRQHandler()` 在 RX FIFO0 有消息时：

```c
if ((interrupts & CAN_IT_RX_FIFO0_MSG_PENDING) != 0U) {
    if ((hcan->Instance->RF0R & CAN_RF0R_FMP0) != 0U) {
        HAL_CAN_RxFifo0MsgPendingCallback(hcan);   // 默认空函数
    }
}
```

默认回调是空的，不会调用 `HAL_CAN_GetRxMessage()` 读取报文，FMP0（FIFO 消息数）不会减少。结果是：

```text
FIFO0 有消息 → 中断持续触发 → ISR 退出后立刻再次进入 → 中断风暴
```

**什么时候会遇到？**

- 本节点只发送、总线上没有其他节点发送：不会触发；
- 总线上有其他节点发送任何帧：滤波器全通过 → 立即触发；
- 接入 CAN 分析仪/其他控制器时很容易遇到。

**解决方案：**

方案 A：如果不需要接收，关闭 RX 中断：

```c
/* 不要调用 HAL_CAN_ActivateNotification(..., CAN_IT_RX_FIFO0_MSG_PENDING) */
```

方案 B：实现接收回调：

```c
void HAL_CAN_RxFifo0MsgPendingCallback(CAN_HandleTypeDef *hcan)
{
    CAN_RxHeaderTypeDef rx;
    uint8_t data[8];

    if (HAL_CAN_GetRxMessage(hcan, CAN_RX_FIFO0, &rx, data) == HAL_OK)
    {
        /* 处理报文 */
    }
}
```

### 9.13 ⚠️ `CAN_TxHeaderTypeDef` 未完全初始化

```c
CAN_TxHeaderTypeDef tx;      // 未初始化
tx.DLC   = 0x08;
tx.IDE   = CAN_ID_STD;
tx.RTR   = CAN_RTR_DATA;
tx.StdId = stdid;
tx.ExtId = 0x000;
```

结构体里还有一个字段 `TransmitGlobalTime` 没有赋值，它的值是栈上的随机值：

- 如果 `USE_FULL_ASSERT` 打开，`assert_param(IS_FUNCTIONAL_STATE(...))` 可能失败；
- 如果随机值等于 `ENABLE`，HAL 会置位 `TGT`（全局时间戳发送位）；
- 在非时间触发模式（TTCM=0）下，TGT 一般无影响，但这是不良习惯。

**改进：**

```c
CAN_TxHeaderTypeDef tx = {0};
```

### 9.14 `CAN_Send_INA226()` 只有声明

`CAN_TASK.h` 里有：

```c
void CAN_Send_INA226(CAN_HandleTypeDef *hcan, uint16_t stdid, float shunt_v,
                     float bus_v, float current, float power);
```

但 `CAN_TASK.c` 里没有实现。当前没有调用，所以不会链接错误；如果以后调用，会报 `undefined reference`。

### 9.15 CAN 总线负载估算

标准帧 8 字节，考虑帧开销和位填充，一帧大约 110~135 位：

```text
1 Mbps → 一帧约 110~135 µs
500 Hz → 每秒 500 帧
总线负载 ≈ 500 × 120 µs = 60 ms/s = 6%
```

所以 1 Mbps 下 500 Hz 发送很轻松。

### 9.16 CAN 调试要点

1. **必须有第二个节点或 CAN 分析仪应答**：CAN 发送需要 ACK，单独一个节点会一直重发，最终 Bus-Off；
2. **终端电阻**：总线两端各 120 Ω，用万用表测 CANH-CANL 约 60 Ω；
3. **共地**：各节点必须共地；
4. **波特率一致**：所有节点必须同为 1 Mbps；
5. **收发器供电**：TJA1050 等需要 5 V，RXD 输出电平要确认与 3.3 V MCU 兼容；
6. **回环测试**：没有总线时，可把 CAN 设为 `CAN_MODE_LOOPBACK` 自测。

## 10. USART2 与 DMA 串口发送 📤

### 10.1 UART 帧格式

本工程：**115200 8N1**

```text
1 位起始位（低）
8 位数据位（低位在前）
1 位停止位（高）
无校验
```

每字节 10 位。

### 10.2 波特率计算

USART2 挂在 APB1，时钟 36 MHz，16 倍过采样：

```text
USARTDIV = PCLK1 / (16 × BaudRate)
         = 36,000,000 / (16 × 115,200)
         = 19.53125
```

BRR 寄存器：

```text
整数部分 = 19
小数部分 = 0.53125 × 16 = 8.5 → 8（实际 HAL 会四舍五入）
实际波特率 = 36,000,000 / (16 × 19.5) = 115,384.6
误差 = (115,384.6 - 115,200) / 115,200 ≈ +0.16%
```

0.16% 误差在 UART 允许范围内（一般 < 2%~3%）。

### 10.3 为什么用 DMA1_Channel7？

STM32F103 的 DMA1 通道与外设请求是固定映射的：

| 通道 | 请求 |
|---|---|
| DMA1_Channel4 | USART1_TX |
| DMA1_Channel5 | USART1_RX |
| DMA1_Channel6 | USART2_RX |
| DMA1_Channel7 | USART2_TX |
| DMA1_Channel2 | USART3_TX |
| DMA1_Channel3 | USART3_RX |

所以 USART2_TX 必须用 **DMA1_Channel7**。

### 10.4 DMA 配置字段

```c
hdma_usart2_tx.Instance = DMA1_Channel7;
hdma_usart2_tx.Init.Direction = DMA_MEMORY_TO_PERIPH;
hdma_usart2_tx.Init.PeriphInc = DMA_PINC_DISABLE;
hdma_usart2_tx.Init.MemInc = DMA_MINC_ENABLE;
hdma_usart2_tx.Init.PeriphDataAlignment = DMA_PDATAALIGN_BYTE;
hdma_usart2_tx.Init.MemDataAlignment = DMA_MDATAALIGN_BYTE;
hdma_usart2_tx.Init.Mode = DMA_NORMAL;
hdma_usart2_tx.Init.Priority = DMA_PRIORITY_LOW;
```

| 字段 | 含义 |
|---|---|
| `Direction` | 内存 → 外设（发送） |
| `PeriphInc` | 外设地址不递增（始终是 USART2->DR） |
| `MemInc` | 内存地址递增（依次发送缓冲区字节） |
| `PeriphDataAlignment` | 外设按字节 |
| `MemDataAlignment` | 内存按字节 |
| `Mode` | 普通模式，传完就停；循环模式会无限重复 |
| `Priority` | DMA 通道仲裁优先级，不是 NVIC 优先级 |

### 10.5 `__HAL_LINKDMA()` 做了什么？

```c
__HAL_LINKDMA(uartHandle, hdmatx, hdma_usart2_tx);
```

展开后大致是：

```c
uartHandle->hdmatx = &hdma_usart2_tx;
hdma_usart2_tx.Parent = uartHandle;
```

这样：

- UART 知道自己的发送 DMA 是哪个句柄；
- DMA 完成中断里能通过 `Parent` 找回 UART 句柄，调用 `HAL_UART_TxCpltCallback()`。

### 10.6 `HAL_UART_Transmit_DMA()` 的工作过程

```text
HAL_UART_Transmit_DMA(&huart2, buf, len)
├── 检查 huart2.gState == READY
├── 检查 hdmatx->State == READY
├── 设置 gState = BUSY_TX
├── 设置 DMA 完成/半完成/错误回调
├── 启动 DMA（内存 → USART2->DR）
└── 立即返回

DMA 传输完成
  → DMA1_Channel7_IRQHandler()
    → HAL_DMA_IRQHandler()
      → UART_DMATransmitCplt()
        ├── 清除 DMAT 位（DMA 不再请求发送）
        └── 使能 USART TC（发送完成）中断

最后一个字节移出移位寄存器
  → USART2_IRQHandler()              // 注意：这一步必须有
    → HAL_UART_IRQHandler(&huart2)
      → UART_EndTransmit_IT()
        ├── 关闭 TCIE
        ├── gState = READY
        └── HAL_UART_TxCpltCallback(&huart2)  // 默认空函数
```

**关键点：**

`UART_DMATransmitCplt()` 在普通模式下**不会**把 `gState` 设回 `READY`，它只是使能 TC 中断。真正把 `gState` 恢复为 `READY` 的是 `UART_EndTransmit_IT()`，而它由 USART2 中断调用。因此：

- 如果 NVIC 里不使能 `USART2_IRQn`，第一帧 DMA 发送完成后 `gState` 会一直停在 `BUSY_TX`；
- 后续每次 `HAL_UART_Transmit_DMA()` 都会返回 `HAL_BUSY`；
- 所以 `USART2_IRQn` 不是“可有可无”，而是 DMA 发送链路的一部分。

### 10.7 ⚠️ `HAL_BUSY` 与缓冲区生命周期

`HAL_UART_Transmit_DMA()` 在以下情况返回 `HAL_BUSY`：

- 上一次 DMA 还没完成（`gState != READY`）；
- DMA 通道还没准备好。

本工程每 2 ms 发 20 字节：

```text
20 字节 × 10 位/字节 = 200 位
200 / 115200 ≈ 1.736 ms
```

2 ms 周期内理论上有 0.264 ms 余量，但比较紧。

**更隐蔽的问题：**

`VOFA_justfloat()` 是**先写 union 缓冲区，再调用** `HAL_UART_Transmit_DMA()`：

```c
data.data1[0] = a;
data.data1[1] = b;
data.data1[2] = c;
data.data1[3] = d;
data.data2[16] = 0x00;
data.data2[17] = 0x00;
data.data2[18] = 0x80;
data.data2[19] = 0x7f;
HAL_UART_Transmit_DMA(&huart2, data.data2, 20);
```

如果上一次 DMA 还没完成，这次写入会**覆盖正在发送的缓冲区**，然后 `HAL_UART_Transmit_DMA()` 返回 `HAL_BUSY`。结果上一帧的后半部分可能被破坏。

**改进：**

- 使用双缓冲/乒乓缓冲；
- 在发送前检查 `huart2.gState == HAL_UART_STATE_READY`；
- 使用发送完成回调置位标志，主循环或下一次中断再发；
- 降低发送频率或提高波特率。

### 10.8 轮询、中断、DMA 三种串口发送方式

| 方式 | API | CPU 占用 | 适用场景 |
|---|---|---|---|
| 轮询 | `HAL_UART_Transmit()` | 高（阻塞） | 少量数据、调试 |
| 中断 | `HAL_UART_Transmit_IT()` | 中（每字节中断） | 中等数据 |
| DMA | `HAL_UART_Transmit_DMA()` | 低（一次启动） | 大量/周期数据 |

本工程选 DMA，是因为每 2 ms 要发 20 字节，用轮询会占用较多 CPU。

### 10.9 为什么必须使能 USART2 中断？

```c
HAL_NVIC_SetPriority(USART2_IRQn, 1, 0);
HAL_NVIC_EnableIRQ(USART2_IRQn);
```

初始化时确实没有使能任何 USART 中断源（RXNEIE、TCIE 等），但 **DMA 发送过程中会自动使能 TC 中断**：

1. `HAL_UART_Transmit_DMA()` 启动 DMA，`gState = BUSY_TX`；
2. DMA 把 20 字节全部搬到 USART2->DR 后，DMA 完成中断触发；
3. `UART_DMATransmitCplt()` 清除 DMAT 位，并使能 `TCIE`；
4. 最后一个字节完全移出移位寄存器后，USART 置位 TC 标志并触发 `USART2_IRQn`；
5. `USART2_IRQHandler()` → `HAL_UART_IRQHandler()` → `UART_EndTransmit_IT()`；
6. `UART_EndTransmit_IT()` 关闭 TCIE，把 `gState` 恢复为 `READY`，调用 `HAL_UART_TxCpltCallback()`。

**如果没有使能 `USART2_IRQn`：**

- TC 标志会一直挂着；
- `gState` 永远停在 `BUSY_TX`；
- 第二帧开始 `HAL_UART_Transmit_DMA()` 全部返回 `HAL_BUSY`；
- 现象是“第一帧有波形，后面再也没有数据”。

所以 `USART2_IRQn` 是 DMA 发送链路的必要环节，不能因为“没有写接收中断”就把它关掉。

## 11. VOFA+ justfloat 上位机协议 📈

### 11.1 VOFA+ 是什么？

VOFA+ 是一个串口/网络数据可视化上位机，支持多种协议：

- **justfloat**：二进制浮点帧，效率高；
- **firewater**：ASCII 文本，调试方便；
- **rawdata**：原始数据。

本工程使用 **justfloat**。

### 11.2 justfloat 帧格式

一帧 20 字节：

```text
[0..3]   float 通道 0，小端
[4..7]   float 通道 1，小端
[8..11]  float 通道 2，小端
[12..15] float 通道 3，小端
[16..19] 帧尾 0x00 0x00 0x80 0x7F
```

帧尾 `0x00 0x00 0x80 0x7F` 按小端解释是：

```text
0x7F800000 = +Infinity（IEEE 754 正无穷）
```

VOFA+ 用这个特殊值作为帧分隔符。

### 11.3 IEEE 754 单精度浮点

`float` 在 Cortex-M3 上是 32 位 IEEE 754：

```text
1 位符号 + 8 位指数 + 23 位尾数
```

例如：

```text
12.5 = 0x41480000
-3.14 = 0xC048F5C3
```

STM32 是小端，所以内存中的字节顺序是低字节在前：

```text
0x41480000 → 00 00 48 41
```

VOFA+ 按小端解析，正好匹配。

### 11.4 union 共享内存技巧

```c
union main
{
    float   data1[4];   // 16 字节
    uint8_t data2[20];  // 20 字节
} data;
```

union 的所有成员从同一地址开始，大小取最大成员：

```text
sizeof(data) = max(16, 20) = 20
```

所以：

- 写 `data.data1[0..3]` → 前 16 字节被 4 个 float 填充；
- 写 `data.data2[16..19]` → 后 4 字节写帧尾；
- 发送 `data.data2` → 得到完整的 20 字节帧。

**为什么用 union？**

- 避免 `float*` 强转到 `uint8_t*` 的严格别名问题；
- 代码直观：一份内存，两种视图；
- C 语言允许 union 类型双关（GCC 支持）。

**注意：**

- `union main` 的标签叫 `main`，但 C 语言的标签（tag）和函数名在不同命名空间，不会冲突；
- 如果把这个文件用 C++ 编译，`union main` 会和 `main()` 冲突；
- 本工程是 C，所以没问题。

### 11.5 发送代码逐行解释

```c
void VOFA_justfloat(float a, float b, float c, float d)
{
    uint8_t i = 0;

    data.data1[i++] = a;   // 通道 0
    data.data1[i++] = b;   // 通道 1
    data.data1[i++] = c;   // 通道 2
    data.data1[i++] = d;   // 通道 3

    data.data2[16] = 0x00; // 帧尾字节 0
    data.data2[17] = 0x00; // 帧尾字节 1
    data.data2[18] = 0x80; // 帧尾字节 2
    data.data2[19] = 0x7f; // 帧尾字节 3

    HAL_UART_Transmit_DMA(&huart2, data.data2, sizeof(data.data2));
}
```

### 11.6 带宽计算

```text
每帧 20 字节
500 Hz → 10,000 字节/秒
115200 8N1 → 11,520 字节/秒（理论）
占用率 ≈ 10,000 / 11,520 ≈ 86.8%
```

余量只有约 13%，比较紧。如果以后增加通道数或提高频率，需要提高波特率（如 460800）或改用更紧凑的协议。

### 11.7 VOFA+ 使用步骤

1. 打开 VOFA+；
2. 选择串口、波特率 115200、8N1；
3. 数据协议选择 **justfloat**；
4. 添加 4 个波形通道；
5. 运行，应该能看到分流电压、总线电压、电流、功率四条曲线。

### 11.8 常见问题

| 现象 | 原因 |
|---|---|
| 没有波形 | 串口选错、波特率不对、协议不是 justfloat |
| 波形乱跳 | 帧尾不对、字节序不对、通道数不匹配 |
| 只有一条线 | 只解析了 1 个 float，或帧尾位置错 |
| 数据全是 0 | INA226 没初始化/没应答 |
| 偶尔断帧 | 带宽接近上限、DMA 忙、缓冲区被覆盖 |

## 12. 数据类型、字节序与溢出 🧮

### 12.1 固定宽度整数类型

```c
#include <stdint.h>

uint8_t   // 0 ~ 255
int8_t    // -128 ~ 127
uint16_t  // 0 ~ 65535
int16_t   // -32768 ~ 32767
uint32_t  // 0 ~ 4294967295
int32_t   // -2147483648 ~ 2147483647
```

在嵌入式里尽量用这些类型，不要用 `int`/`long`，因为它们的宽度随平台变化。

### 12.2 `int16_t` 溢出：本工程的两个临界值 ⚠️

CAN 发送前做了缩放：

```c
send_shunt = (int16_t)(shunt_volt * 1000.0f);  // mV
send_bus   = (int16_t)(bus_volt   * 1000.0f);  // mV
send_curr  = (int16_t)(current    * 1000.0f);  // mA
send_power = (int16_t)(power      * 100.0f);   // 0.01 W
```

`int16_t` 最大值 32767：

| 数据 | 缩放 | 溢出阈值 |
|---|---|---|
| 分流电压 | ×1000 | ±32.767 mV（实际最大 ±81.92 mV，**可能溢出**） |
| 总线电压 | ×1000 | **32.767 V** |
| 电流 | ×1000 | 32.767 A（设计最大 32.7 A，刚好不溢出） |
| 功率 | ×100 | **327.67 W** |

**结论：**

- 总线电压超过 **32.767 V**，CAN 数据会变成负数；
- 功率超过 **327.67 W**，CAN 数据会变成负数；
- 分流电压超过 **32.767 mV** 也会溢出（在 1 mΩ、32.7 A 时压降约 32.7 mV，接近临界！）；
- VOFA+ 通道发送的是原始 float，不受这些缩放影响。

> 注意：分流电压在 32.7 A、1 mΩ 时是 32.7 mV，`32.7 × 1000 = 32700`，刚好在 32767 以内。但如果采样电阻是 5 mΩ，32.7 A 时压降 163.5 mV，`×1000 = 163500`，严重溢出。所以这个 CAN 协议只适合小采样电阻、低电压、低功率的场景。

### 12.3 浮点到整数的转换

```c
int16_t x = (int16_t)(12.9f);   // 12，向零截断
int16_t y = (int16_t)(-12.9f);  // -12，向零截断
```

C 的强制转换是**截断**，不是四舍五入。如果需要四舍五入：

```c
int16_t x = (int16_t)(value + 0.5f);
int16_t y = (int16_t)(value - 0.5f);  // 负数
```

### 12.4 有符号右移的可移植性问题

打包 CAN 数据时：

```c
Data[0] = ((num1) >> 8);
```

`num1` 是 `int16_t`，负数右移在 C 标准里是 **implementation-defined**（实现定义）。ARM GCC 使用算术右移（高位补符号位），所以负数的 `>> 8` 得到 `0xFF` 高字节，结果正确。

更可移植的写法：

```c
Data[0] = (uint8_t)((uint16_t)num1 >> 8);
Data[1] = (uint8_t)((uint16_t)num1 & 0xFF);
```

先把有符号数转成无符号，再移位，避免实现定义行为。

### 12.5 小端 CPU 与大端协议

- STM32 是小端：低字节在低地址；
- 本工程 CAN 数据区手动按大端打包；
- VOFA+ justfloat 使用小端 float；
- INA226 寄存器数据是大端（高字节在前）。

同一个工程里三种端序同时存在，必须逐处确认。

### 12.6 `float` 精度

`float` 有 24 位有效尾数，约 7 位十进制有效数字：

```text
0.1f 不能精确表示
1234567.0f 可能丢失精度
```

本工程测量值范围小（电压几十伏、电流几十安），`float` 足够。如果要做高精度电能计量，考虑用定点数或 `double`。

### 12.7 `volatile` 与中断共享变量

如果一个变量在 ISR 里修改、在主循环里读取，应该加 `volatile`：

```c
volatile float g_bus_voltage;
```

否则编译器可能把它缓存到寄存器，主循环永远看不到更新。

本工程的 `shunt_volt`、`bus_volt`、`current`、`power`、`send_*` 都是全局变量，但只在 ISR 内使用，主循环不读，所以不加 `volatile` 也能工作。如果以后在主循环里打印这些值，建议加 `volatile` 或用临界区保护。

**注意：**

- `volatile` 只保证“每次都从内存读写”，不保证原子性；
- 多字节变量（`float`、`int32_t`）在 ISR 和主循环之间读写时，可能需要关中断保护；
- 本工程的 `float` 在 Cortex-M3 上读写是 32 位对齐的，单次读写是原子的，但“读-改-写”不是。

### 12.8 `static` 与文件作用域

```c
static float g_CurrentLSB = 0.0f;       // 只在本文件可见
static const BoardConfig_t board_conf[] = { ... }; // 只在本文件可见，放在 Flash
```

- `static` 修饰全局变量/函数：限制链接可见性，避免命名冲突；
- `static const` 数组：通常放在 Flash（`.rodata`），不占 RAM；
- 本工程的 `board_conf` 和 `g_CurrentLSB` 都是 `static`，很好的做法。

### 12.9 `union` 类型双关

C 语言允许：

```c
union {
    float f;
    uint8_t b[4];
} u;

u.f = 1.0f;
// 读取 u.b[0..3] 得到 1.0f 的字节表示
```

这是本工程 VOFA 发送的基础。

**注意：**

- C99 起，union 类型双关是允许的（实现定义，但 GCC 明确支持）；
- C++ 中读取非活跃成员是 UB；
- 不要用 `float*` 强转 `uint8_t*` 再解引用，可能违反严格别名规则。

## 13. 调试与排错 🛠️

### 13.1 调试接口

- 使用 **SWD**：SWDIO（PA13）、SWCLK（PA14）、GND、3.3V；
- ST-Link、J-Link、CMSIS-DAP 都支持；
- PlatformIO 默认使用 ST-Link：

```bash
pio run -t upload

```

### 13.2 `Error_Handler()` 断点

如果程序停在：

```c
__disable_irq();
while (1) { }
```

说明某个 `HAL_xxx_Init()` 失败了。查看调用栈，常见原因：

- HSE 晶振没起振；
- I2C/CAN/USART 初始化参数错误；
- 时钟配置失败。

### 13.3 HardFault 排查

进入 `HardFault_Handler()` 时：

1. 查看 LR 寄存器，判断使用的是 MSP 还是 PSP；
2. 找到对应的栈指针；
3. 栈里保存的 PC 就是出错指令地址；
4. 用 `addr2line` 或 IDE 反汇编定位。

常见原因：

- 空指针/野指针；
- 数组越界；
- 栈溢出；
- 未对齐访问；
- 调用了未实现的函数。

### 13.4 CAN 发不出去

| 检查项 | 说明 |
|---|---|
| 终端电阻 | CANH-CANL 约 60 Ω |
| 第二个节点 | 没有 ACK 会一直重发 |
| 波特率 | 所有节点一致 |
| 收发器供电 | 5 V/3.3 V 是否正确 |
| TX/RX 接线 | PA12→TXD，PA11←RXD，不要接反 |
| 模式 | `CAN_MODE_NORMAL`，不是 Loopback/Silent |
| 滤波器 | 发送不受滤波器影响，但接收需要 |
| Bus-Off | 读 ESR 寄存器，检查 BOFF 位 |

### 13.5 I2C 读不到 INA226

| 检查项 | 说明 |
|---|---|
| 供电 | INA226 VCC 3.3 V/5 V |
| 地址 | A0/A1 接法，0x80 是 8 位地址 |
| 上拉 | SCL/SDA 是否有 2.2~4.7 kΩ 上拉 |
| 接线 | SCL→PB6，SDA→PB7 |
| 共地 | MCU 与 INA226 必须共地 |
| 总线状态 | 用示波器看 SCL/SDA 是否被拉死 |
| I2C 扫描 | 用 `HAL_I2C_IsDeviceReady()` 扫描地址 |

### 13.6 串口乱码/无输出

| 检查项 | 说明 |
|---|---|
| 波特率 | 115200 |
| 数据格式 | 8N1 |
| TX/RX | PA2→RX，PA3←TX（交叉） |
| 共地 | USB-TTL 与板子共地 |
| 电平 | 3.3 V TTL，不是 RS-232 |
| DMA | `HAL_UART_Transmit_DMA()` 返回值是否 HAL_OK |
| 缓冲区 | 是否被提前覆盖 |

### 13.7 VOFA+ 没有波形

| 检查项 | 说明 |
|---|---|
| 协议 | 选择 justfloat |
| 波特率 | 115200 |
| 通道数 | 4 |
| 帧尾 | `00 00 80 7F` |
| 数据 | 先确认串口助手能收到 20 字节二进制 |

## 14. 设计复盘：原工程的坑与改进方向 🧐

### 14.1 已发现的问题清单

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | TIM1 中断里阻塞读 4 次 I2C | 占用 0.4~0.5 ms，可能卡死 | 移到主循环/DMA |
| 2 | CAN RX 中断使能但无回调 | 收到帧会中断风暴 | 实现回调或关闭 RX 中断 |
| 3 | `HAL_CAN_ErrorCallback` 不会执行 | Bus-Off 软件恢复无效 | 使能 ERRIE + CAN1_SCE |
| 4 | `CAN_TxHeaderTypeDef tx` 未初始化 | `TransmitGlobalTime` 随机 | `= {0}` |
| 5 | `send_bus`/`send_power` 溢出 | >32.767 V / >327.67 W 变负数 | 改 int32 或换缩放 |
| 6 | `HAL_UART_Transmit_DMA` 忙时覆盖缓冲区 | 帧损坏 | 双缓冲/检查状态 |
| 7 | 忽略 `CAN_send()`/`INA226_Init()` 返回值 | 错误不可见 | 检查返回值 |
| 8 | `CAN_Send_INA226()` 只有声明 | 调用会链接错误 | 实现或删除 |
| 9 | INA226 读失败返回 0.0 | 无法区分故障和真 0 | 返回状态 + NaN |
| 10 | 全局变量未加 `volatile` | 主循环读取可能读到旧值 | 加 `volatile` |
| 11 | 没有看门狗 | 死机无法恢复 | 加 IWDG |
| 12 | 没有读取 INA226 ID | 无法确认芯片 | 读 0xFE/0xFF |
| 13 | CAN 协议无序号/CRC | 丢帧/错帧无法检测 | 加应用层协议 |
| 14 | `union main` 命名 | C++ 下冲突 | 改名 `vofa_frame_t` |
| 15 | `MX_GPIO_Init` 使能 GPIOD | 无害但多余 | 可去掉 |

### 14.2 改进后的架构建议

**方案 A：前后台（最简单）**

```text
TIM1 中断：只置位 g_sample_flag
主循环：
  if (g_sample_flag) {
      g_sample_flag = 0;
      读 INA226
      发送 CAN
      发送 VOFA
  }
```

优点：I2C 不再阻塞高优先级中断。
缺点：主循环有延迟，500 Hz 下仍要保证及时处理。

**方案 B：I2C DMA + 状态机**

```text
TIM1 中断：启动 I2C DMA 读
I2C DMA 完成中断：解析数据、启动下一次
```

优点：CPU 占用低。
缺点：代码复杂。

**方案 C：FreeRTOS**

```text
采集任务（中优先级）
CAN 发送任务
VOFA 发送任务
```

优点：结构清晰，易于扩展。
缺点：增加 RAM/Flash 开销和调度复杂度。

### 14.3 CAN 应用层协议建议

当前协议只有 4 个 int16，建议增加：

```text
Byte 0：帧类型/序号
Byte 1：状态标志
Byte 2..7：数据
```

或者使用结构化的多帧协议：

```text
0x605：电压/电流
0x606：功率/温度
0x607：状态/故障码
```

并增加：

- 序号（检测丢帧）；
- CRC（检测错帧）；
- 时间戳（同步）；
- 故障码（过压/过流/过温）。

| INA226 功率 LSB | 25 × Current_LSB | ≈ 24.95 mW |
| VOFA 带宽 | 20 B × 500 Hz | 10,000 B/s |
| UART 理论带宽 | 115200 / 10 | 11,520 B/s |
